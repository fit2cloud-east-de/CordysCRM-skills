# 订单操作合集

> 本文档是订单业务操作的唯一专项流程入口。先按用户意图选择下方一个操作：创建/新建订单、按合同生成订单、拆订单执行“创建订单 / 自动拆单”；完整订单明细、全量同步或订单导出执行“完整订单导出”。普通订单查询仍走 `core/query-engine.md`，更新已有订单仍走 `core/write-engine.md`。
>
> **订单导出优先级**：一旦用户明确要求“导出订单”“全部订单”“完整订单明细”或“全量同步”，必须执行本文档的“完整订单导出”，本文档中的全量分页、父子表整理和交付要求优先于 `SKILL.md`、`core/query-engine.md`、`core/cli-spec.md`、`core/output-engine.md` 中针对普通查询/大结果集的展示限制。不得把订单导出降级为只展示当前页，也不得以“技能不支持本地导出”为由拒绝；只有分页、字段或映射校验失败时才交付部分结果，并只说明数据未完整，除非用户明确要求排查原因。
>
> 通用字段结构、确认红线和失败处理继续复用 `core/write-engine.md` §0.2、§0.4、§7、§8；订单专属规则与其冲突时以本文档为准。

## 操作路由

| 用户意图 | 执行章节 | 结果 |
|---|---|---|
| 创建订单、按合同生成订单、拆订单 | 创建订单 / 自动拆单 | 创建一张或多张新订单，并按规则回写合同状态 |
| 全部订单、完整订单明细、全量同步、订单导出 | 完整订单导出 | 保留全部父订单和子表行，交付两张关联数据表 |
| 查看订单、搜索订单、订单数量或订单统计 | `core/query-engine.md` + `core/cli-spec.md` | 按普通查询或统计口径返回，不自动做文件导出 |

不要把“创建订单 / 自动拆单”理解成“完整订单导出”里的“拆出订单父表和子表”；前者是写入 CRM 生成订单，后者是读取 CRM 整理交付数据。

## 创建订单 / 自动拆单

### 0. 当前边界

- 不按合同类型判定是否拆单；对目标合同的六类业务子表统一执行确定性分组。
- 分组键固定为：**产品类型 ID + 收入类型中文标签**。同一组合的多条合同子表行合并到同一张订单，不同组合分别生成订单；同一业务产品即使来自不同子表或不同产品/服务选择器也必须归入同组。
- “产品类型”取每条合同子表行的同名字段。PRICE 型“产品/服务”保存的是价格目录主 ID，不是具体产品身份：它与 `price_sub` 共同保留在各源行并写入对应订单子表，但绝不进入拆单键。这样共享同一 PRICE 目录的不同产品不会误合并，“其他”等其他子表中的同一产品也不会被重复拆单。收入类型必须先由合同 option ID 归一为中文标签再参与分组。
- 每张订单仍使用 §1.1 的既有名称模板，**订单名不追加收入类型**。
- 一次 `crm create order` 必须覆盖合同全部有效业务子表行并顺序创建全部分组。全部订单成功后才把合同“是否已拆订单”更新为“是”；不自动回写子表“关联订单编号”。
- 合同已是“是否已拆订单=是”时创建前关闭失败，防止重复订单。部分成功或状态不明时停止后续组并返回已创建订单 ID，禁止整批自动重跑。

### 1. 固定业务规则

按以下优先级组装字段：**订单名固定模板与合同继承规则 > 用户显式输入 > 本 SOP 默认值 > 表单校验**。负责人、收入类型和服务属于合同继承规则，用户不得用任意值覆盖。

### 1.1 订单名

- 不让用户自由填写订单名，也不把订单名本身列为待补充项；SOP 必须在确认前自动组装并展示完整名称。
- 每张最终订单 POST 请求体顶层 `name` **不能为空**，由 CLI 自动生成并校验，固定格式为：`<合同编码>-<产品类型中文标签>-${订单编号}`。外层自动拆单请求不手填自由格式 `name`。
- 示例：`DQ20260805X004-JumpServer 企业版-${订单编号}`。
- 第一段取本张订单 `moduleFields` 中“合同编码”字段的实际值；第二段取本张订单用于命名的产品类型**中文标签**，不得使用产品 ID。
- 第三段 `${订单编号}` 是固定字面量，必须原样交给后端；本地不得插值、替换成真实编号或删除 `$`、`{`、`}`。
- 一张订单必须先确定唯一的命名产品类型。CLI 用拆单键中的“产品类型”ID 查询当前产品目录取得中文名；缺合同编码、缺产品类型或产品 ID 无法唯一反查中文标签时，必须在首次 POST 前停止，不得猜测。
- 用户要求手工指定其他名称时，说明当前 SOP 只允许固定模板；不得绕过模板写入自定义名称。

### 1.2 缺省字段

| 业务字段 | `forms/order.md` 表单字段 | 缺省值 |
|----------|-------------------------|--------|
| 交付团队 | 交付团队 | 线下团队 |
| 交付形式 | 交付形式 | 远程交付 |
| 正式 License 申请状态 | 正式license申请状态 | 未申请 |
| 是否专项交付 | 是否专项交付 | 否 |

执行规则：

1. 用户明确指定该字段时保留用户值；未指定或值为空时才补缺省值。
2. 先执行 `sync-if-needed`，再从当前本地 `references/forms/order.md` / `field-schema.json` 解析字段 ID 和选项 ID；不得把中文标签直接当 `fieldValue`，也不得把本文档写死成实例 ID。
3. 字段或缺省选项无法唯一解析时立即停止，不发送 create 请求，并明确指出缺失的字段或选项。
4. `crm create order` 会为每个分组生成并校验 `name` 的合同编码前缀、产品类型中文标签和固定 `${订单编号}` 后缀，并补齐缺失的四项缺省值，作为 SOP 的最后防线；上层仍须在确认表中展示每张订单实际名称。

### 1.3 合同继承与子表必填

| 订单目标 | 合同来源 | 传值规则 |
|----------|----------|----------|
| 顶层 `owner` | 合同详情顶层 `owner` | 原样传合同负责人的 **userId**；`ownerName` 只展示，不得当值传入 |
| 顶层“收入类型” | 生成本张订单的合同子表行“收入类型” | 先把合同子字段选项 ID 解析为中文标签，再在订单顶层“收入类型”选项中按标签取目标 ID |
| 订单子表行“收入类型” | 对应合同子表行“收入类型” | 按中文标签映射到目标订单父子表下的选项 ID，不得假设合同和订单的 option ID 相同 |
| 订单子表行“服务” | 对应合同子表行“服务” | 对 `维保`、`专业服务`、`培训服务` 原样传 DATA_SOURCE 服务 ID；合同/订单子 fieldId 不同，必须按“父表标签 + 子字段标签”换成订单 fieldId |

执行规则：

1. 订单负责人必须与合同负责人一致。合同详情缺少非空 `owner` 时停止；不得省略后让后端改用当前创建人，也不得传 `ownerName`。
2. 每张订单必须确定唯一收入类型。相同产品类型出现多个收入类型时按标签拆成多张订单；同一分组内所有合同源行收入类型必须一致，不得任选一个或覆盖子表。
3. 顶层收入类型和每个订单子表行收入类型必须使用同一中文标签，但分别按各自目标字段的 options 解析 ID。目标标签无法唯一解析时停止。
4. `维保`、`专业服务`、`培训服务` 子表中的“服务”按业务规则视为**必填**，即使同步表单元数据把该子字段标为非必填也不得省略。合同对应行已有服务时继承其 ID；为空时一次性列入待补充项，确认具体服务 ID 后才能创建。
5. 不得用产品类型、产品 SKU、子表名称或“销售品”代替服务；也不得把合同子 fieldId 直接写进订单子表行。
6. `crm create order` 在首次 POST 前再次要求非空 `owner`、顶层收入类型、每个有效子表行的收入类型，以及含“服务”字段子表行的服务 ID；任一缺失或顶层/子表收入类型不一致时关闭失败。

#### 1.3.1 所有子表按同步 form 完整映射

- 字段映射以 `sync-if-needed` 后的本地 `references/forms/contract.md`、`references/forms/order.md` 和 `references/field-schema.json` 为依据；截图只用于发现异常，不能作为字段清单或 fieldId 来源。
- 遍历订单 form 中的**全部** `SUB_*` 父字段。当前包括“订阅”“授权及一体机”“维保”“专业服务”“培训服务”“其他”，但实现不得只为“培训服务”写分支，也不得把六个父 fieldId 写死。
- 先按父表中文标签定位合同源子表与订单目标子表，再按子字段中文标签逐列映射。合同源行中每个有值且目标子表存在同标签字段的非 `FORMULA` 业务字段都要保留，包括产品/服务、产品类型、产品SKU、产品版本、描述、购买方式、收入类型、售卖类型、服务等级、币种、成交指导价、合同约定价、税率、单位、数量、年限、折扣、最终客户等。
- 不得把源行缩减成“公式刚好能算”的最小字段集，也不得只复制订单 form 标记为必填的字段。源合同已有的可映射业务值即使在订单 form 中选填，也必须写入订单目标行。
- 合同源字段为 `SELECT/RADIO` 时必须先执行“合同 option ID → 合同中文标签”。订单目标仍为 `SELECT/RADIO` 时再映射同标签的目标 option ID；目标为 `INPUT/TEXTAREA` 时写入标签文本，例如合同“币种/单位”的 ID 必须写成订单“其他”子表的 `CNY/年`。枚举源值遇到数字、日期、数据源等不兼容目标类型时关闭失败，不得原样写 ID。`DATA_SOURCE` 保留实体 ID；其他文本、数字、日期等按订单目标类型校验后保留值。
- 合同公式结果、合同侧流程控制字段“拆分规则”、回写字段“关联订单编号”和合同子表行 `id` 不复制；订单行 `id` 由后端新生成。**`price_sub` 不是新订单行 ID，而是合同 PRICE 数据源子行的关联键，必须从精确匹配的合同源行原样保留。** 所有订单 `FORMULA` 按 §1.4 由订单公式重新计算。除这些明确排除项外，合同有值字段若在订单目标子表找不到同标签字段，必须列为映射冲突，不得静默丢弃。
- 产品/服务字段带出的 `*_ref_*` 是只读引用投影，不是普通可写列。CLI 读取合同详情，用“父表标签 + 子字段标签”取得这些值供必填校验和公式计算；公式完成后从最终 POST 行中剥离，由 Cordys 根据“产品/服务 ID + `price_sub`”重新解析。不得把投影字段显式写入后端并期待其原样保存。
- 目标 form 的必填业务字段在合同源行中没有值，或源/目标父表及子字段标签无法唯一匹配时，必须在首次 POST 前一次性列出所有缺项并停止。

### 1.4 所有子表及订单主表公式必须在首次提交前算完

订单的各个子表都是独立表单，各自公式可能引用不同原字段。CLI 先按 §1.3.1 从合同精确源行生成完整的非公式业务字段；只有 `FORMULA` 结果不复制，由 CLI 在每张订单首次且唯一一次 POST 之前统一计算。

执行规则：

1. CLI 获取当前 `/order/module/form` 后，动态遍历 payload 中所有有数据的订单子表、每一行和表单内全部 `FORMULA` 字段；不得只处理“培训服务”，不得写死六张子表的 fieldId，也不得假设各子表使用同一公式。表单新增公式时，即使本地精简 schema 尚无该公式字段，也必须计算并写入最终 body。
2. 先完成每个活动子表行的全部公式，再计算订单顶层全部公式。当前至少包括：`累计原始订单金额` = 所有订单子表行“最终成交价（含税）”之和；`有效订单金额` = `累计原始订单金额 - 调整金额`。没有数据的子表对聚合贡献 `0`，不能因为截图只展示一类子表就漏掉其他类型。
3. 合同“调整金额”是本次全部订单共享的全局金额；缺值按 `0`。CLI 先以调整金额 `0` 计算每组累计原始订单金额，再按“本组原始金额 / 全部分组原始金额”比例分摊合同调整金额。除最后一组外向 0 截断到两位小数，最后一组吸收尾差，保证各单调整金额之和与合同完全一致；非零调整但总原始金额为 `0`、存在负分组金额或精度超过两位时停止且不发送 POST。
4. 公式按当前 `formula.ir` 求值，支持子表公式引用公式、主表公式引用子表聚合或其他主表公式；调用方传入的任何旧公式值都不可信，CLI 必须覆盖重算。最终 POST body 中必须已经包含每行公式结果及主表公式的实际存储位置，不能等待创建后的编辑请求补算；带 `businessKey` 的主表公式写对应顶层字段，不重复塞进 `moduleFields`。
5. 对公式最终引用的每个原始字段逐项校验：字段必须存在且非空，值必须是可计算的有限数字；`NaN`、`Infinity`、布尔值、对象、数组和非数字文本均不允许。任何除法的实际除数不得为 0。订阅年限、维保年限、订阅/维保年限、数量、税率、折扣或调整金额等只要被当前公式引用，就属于计算必需输入。`INPUT_NUMBER.numberFormat=percent` 按 Cordys 表单语义参与运算：业务值 `6` 原样保存，但公式操作数为 `0.06`，不得要求调用方篡改成 `0.06`。
6. 公式缺定义、IR 无效、引用循环、未知函数/节点/运算符、源字段缺失、非有限数字、除 0 或结果无法按当前精度保存时，关闭失败并且不发送 POST；错误必须指出主表/子表、行号、公式和源字段，便于一次补齐。
7. 精度优先使用当前公式定义；未显式提供时按当前 CRM 行为保留两位小数并向 0 截断。示例：`6500 / 1.06` 写为 `6132.07`，对应税额写为 `367.92`。
8. 子表行 `id` 由创建成功后的系统生成，创建前不得复制合同源行 `id`；`price_sub` 必须从匹配的合同 PRICE 源行继承并随 create 提交。两者不能再作为同一类“后端生成字段”处理。
9. 当前“累计原始订单金额”的 form 字段带 `businessKey=amount`，因此计算结果写请求顶层 `amount`；“有效订单金额”没有 businessKey，继续写 `moduleFields`。实现按当前 form 的 `businessKey` 动态决定存储位置，不写死字段 ID。

### 2. 创建流程

### 步骤 1：定位唯一合同

1. 执行 `cordys_ext.sh sync-if-needed`。
2. 用户给出合同 ID 时直接 `crm get contract <ID>`；只有名称或编码时先 `crm page contract` 定位。
3. 0 条时停止；多条时展示合同名、合同编码、客户、合同类型相关字段，让用户选择；禁止猜合同 ID。
4. 读取合同详情，取得 `contractId`、`customerId`、合同编码、`owner`、`ownerName` 及全部目标合同子表完整行；不要只读取扁平化产品列表。

### 步骤 2：核对已有订单

- 已知 `customerId` 时执行 `crm acct-sub order <customerId>`，在返回记录中核对 `contractId`、订单编号、产品和金额。
- 创建前不得把含固定 `${订单编号}` 占位符的待提交 `name` 当作唯一查重条件；应以 `contractId`、客户、产品和创建时间等字段核对。
- 当前接口无法可靠按合同列出订单时，不得宣称“该合同没有订单”；在确认表中写明已完成客户维度核对及其限制。

### 步骤 3：形成订单草稿

1. 读取同步后的 `references/forms/contract.md` 与 `references/forms/order.md`，取得两侧顶层字段、全部子表、必填规则和 SELECT/RADIO 选项；不要从截图整理字段清单。
2. 遍历合同详情中全部有效业务子表行，按“父表标签 + 子字段标签”定位订单目标子表；完整保留源行上下文，不要凭相似 fieldId 或扁平化同名字段复制。合同“产品表格”是汇总表，不生成订单行。
3. 对每行提取产品类型 ID 和收入类型中文标签，以 `(产品类型 ID, 收入类型标签)` 分组；产品/服务目录 ID 与 `price_sub` 只保留为该源行的写入关联信息。同组多行可跨子表合并，不同组形成不同草稿；禁止让模型自行任选或合并组合。
4. 为每组用产品类型 ID 查询当前产品目录，按 §1.1 的原模板组装完整 `name`；名称不追加收入类型。随后应用四项缺省值。
5. 按 §1.3 继承合同负责人，并将本组收入类型标签分别映射到订单顶层和本组全部目标子表行。
6. 对 `维保`、`专业服务`、`培训服务` 的每个目标行继承非空服务 ID；缺服务时停止，不得提交空行。
7. 按 §1.3.1 映射本组源行全部有值的非公式业务字段，而不是只传价格、数量、收入类型和服务；不同子表的同名子字段不得混用。不要复制合同源行 `id`，但必须保留其 `price_sub`。
8. 每组先按调整金额 `0` 重算子表和主表公式，再按 §1.4 的比例规则分摊合同全局调整金额并二次重算有效订单金额。全部草稿和公式必须在首次 POST 前形成；任一组失败时本批写请求为 `0` 次。

### 步骤 4：校验并一次性补充

- 对照同步后的 contract/order form 校验 `customerId`、`contractId`、`owner`、顶层收入类型、目标子表完整行、源合同所有有值业务字段均已映射、每行收入类型、服务 ID、其他必填字段、SELECT 选项和金额；同时核对当前公式引用的价格、数量、年限、折扣、税率、调整金额等原字段均有非空且可计算的有限数字，除数不为 0。
- 一次性列出所有无法从合同、用户输入和现行规则确定的字段；不要逐字段追问。
- 不向用户追问自由格式的 `name`；但缺少组装 `name` 所需的合同编码或唯一产品类型中文标签时，必须列入待补充信息并停止提交。

### 步骤 5：展示并确认

创建前必须展示：合同、客户、预计创建订单数，以及每张订单的产品/服务、金额和全部业务字段。至少明确显示以下十二项：

| 字段 | 值 | 来源 |
|------|----|------|
| 订单名 | `<合同编码>-<产品类型中文标签>-${订单编号}` 的完整待提交值 | 固定模板 |
| 负责人 | 合同负责人姓名 + userId | 合同 `ownerName` + `owner` |
| 顶层收入类型 | 从目标合同子表行解析出的唯一中文标签 | 合同子表继承 |
| 子表收入类型 | 每行标签及订单目标选项 ID | 合同子表继承/目标字段映射 |
| 服务 | `维保`、`专业服务`、`培训服务` 每行的服务名称 + 服务 ID | 合同子表继承；必填 |
| 调整金额 | 本组按原始金额比例分摊值；最后一组吸收尾差 | 合同全局调整金额/CLI 计算 |
| 累计原始订单金额 | 全部目标子表最终成交价（含税）之和 | 主表公式预计算 |
| 有效订单金额 | 累计原始订单金额 - 调整金额 | 主表公式预计算 |
| 交付团队 | 线下团队或用户指定值 | 默认/用户 |
| 交付形式 | 远程交付或用户指定值 | 默认/用户 |
| 正式 License 申请状态 | 未申请或用户指定值 | 默认/用户 |
| 是否专项交付 | 否或用户指定值 | 默认/用户 |

用户回复“确认”或“提交”后才执行。多张订单必须先展示精确数量和逐单划分，一次确认只覆盖当前展示的草稿；字段或数量变化后重新确认。

### 步骤 6：组装并顺序提交

一次确认对应一次自动拆单请求。调用方只传唯一合同 ID，以及需要覆盖四项默认值的公共订单字段；**不要手传 `name`、`owner`、产品、收入类型、调整金额、订单子表行、公式或 `moduleFormConfigDTO`**。这些分组相关字段全部由 CLI 从合同详情生成：

```json
{
  "contractId": "<合同ID>",
  "moduleFields": [
    {"fieldId": "<交付团队字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<交付形式字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<正式license申请状态字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<是否专项交付字段ID；可省略>", "fieldValue": "<用户指定选项ID>"}
  ]
}
```

请求固定通过 UTF-8 stdin 提交：

```bash
printf '%s' '{"contractId":"<合同ID>","moduleFields":[]}' | cordys.sh crm create order @-
```

- CLI 在首个写请求前一次性读取订单 form、合同详情、产品目录和合同 form，生成全部分组的最终 POST body；任一字段、映射、产品名称、`price_sub`、公式或金额分摊不能完成时本批写请求为 `0` 次。
- 最终每张订单都必须含现有模板 `name`、合同 `owner/customerId/contractId`、本组唯一顶层收入类型、本组全部子表行及其 `price_sub`、分摊调整金额、全部子表与主表公式，以及当前 `moduleFormConfigDTO`。名称末尾仍是固定字面量 `-${订单编号}`，不包含收入类型。
- 多张订单按合同源行首次出现的分组顺序逐张创建，不并行提交；每张最多发送一次 POST，取得 `code=100200` 且非空 `data.id` 后才创建下一张。
- 任一订单失败或状态不明时立即停止，输出已创建订单 ID、失败分组和未执行分组，并标记 `retryAllowed:false`；不得整批自动重跑。
- 只有全部订单均成功，才读回最新合同、保全完整顶层字段和子表、附加当前合同 `moduleFormConfigDTO`，将“是否已拆订单”更新为“是”。该合同 update 最多发送一次；失败时不得重新创建订单，只能查证后单独处理合同标记。
- `splitByProductIncome:false` 只保留给旧版已物化单订单 payload 的兼容诊断；运行时 SOP 不得使用它绕过自动拆单。

### 步骤 7：核验结果

- `code:100200` 才视为成功，保存订单 ID，并用该 ID 执行一次 `crm get order <ID>`，核对负责人、顶层收入类型、目标子表全部业务字段与公式结果，以及累计原始订单金额、有效订单金额已落库；响应未返回后端替换占位符后的订单名/编号时一并核对。
- HTTP 500、超时或状态不明时，先按客户维度重新查询订单，并结合 `contractId`、创建时间、产品和金额核对；未确认未落库前禁止重试。
- 批次响应中的 `createdOrders` 是已确认成功的订单清单；无法证明成功或失败时停止后续订单创建，向用户报告已成功数量、状态不明分组和未执行数量。`retryAllowed:false` 表示禁止重新运行整个 `crm create order`；若仅合同回写失败，先查证后只处理合同字段。
- 全部创建及合同回写成功时，响应必须同时满足 `code:100200`、`writeState:complete`、`contractSplitUpdated:true`，并返回每张订单的分组键、名称、金额和 `orderId`。

### 3. 当前拆单规则摘要

| 规则项 | 当前行为 |
|--------|----------|
| 合同分类 | 不按合同类型分支；所有目标合同统一处理 |
| 分组键 | 产品类型 ID + 收入类型中文标签；PRICE 目录主 ID 不参与 |
| 同组多行 | 合并到一张订单，保留全部源行 |
| 订单名称 | 继续 `<合同编码>-<产品类型中文标签>-${订单编号}`，不追加收入类型 |
| 字段继承 | 合同 owner/customerId/contractId + 本组完整非公式子表字段；保留 `price_sub` |
| 公式 | 每组独立重算全部子表公式、累计原始订单金额和有效订单金额 |
| 调整金额 | 按各组原始金额比例分摊，除末组外向 0 截断两位，末组吸收尾差 |
| 创建顺序 | 首次出现顺序串行；任一失败/不明立即停止，禁止整批重跑 |
| 合同回写 | 全部订单成功后才把“是否已拆订单”更新为“是”；不回写子表关联订单编号 |

## 完整订单导出

### 2.1 适用范围与数据源

用户明确要求“全部订单”“完整订单明细”“全量同步”或“导出订单”时执行本节。全局订单列表固定使用 `crm page order`，对应 `POST /order/page`；该入口沿用当前用户角色权限、筛选条件和排序，从 `current:1` 开始受控分页。普通查看只取当前页；本节必须连续分页直到首个响应的 `data.total` 完整命中。

`POST /account/order/page` 是客户维度的订单列表接口，只用于 `crm acct-sub order <客户ID> [JSON]`，请求体由 CLI 在顶层注入 `customerId`。它不是全局订单导出接口。不得把 `/account/order/page` 写入全局 `crm page order` 的调用模板，也不得把全局导出改成逐客户枚举，除非用户明确要求按客户拆分查询。

每页最多请求 500 条，首个响应的 `data.total` 作为目标总数。保存每页完整响应中的父订单对象，不得只保存展示列；父对象的 `moduleFields`、数组型 `fieldValue[]`、每个子表行的全部字段和行内 `id` 必须原样保留。页码连续、`total` 未变化、没有未达目标的空页，且按父订单 `id` 去重后的数量等于首个 `total` 后，才可进入整理步骤。任何请求失败、响应结构异常、重复 ID、缺页或 total 变化都必须停止，不能把部分页交付为全量。

### 2.2 父子数据整理

订单列表的每个 `data.list` 项是一条父订单；每个数组型 `moduleFields[].fieldValue[]` 对应的对象是一条子表行。父表与子表必须分别落表：

- `订单明细`：一条订单一行，保留固定父表字段和订单 `id`、`contractId` 等原始关联键。
- `订单子表明细`：一条子表行一行，保留父订单关联键、父 `fieldId` 对应的 `子表名称`、从 1 开始的 `子表行号`、子表行对象 `id` 对应的 `子表行ID`，以及该行全部字段。

没有子表行时仍交付带表头的空 `订单子表明细`。`price_sub` 是价格目录子行关联键，固定列名为 `字段 price_sub`；它不能改名为“合同价格行ID”，也不能当作 `子表行ID`。

#### 2.2.1 父表字段范围

父表必须输出“固定父表头”中的全部字段：订单身份与关联字段（订单名、订单编号、订单 ID、客户、合同、合同 ID）、金额字段、法人实体与收入类型、交付与履约字段、联系人字段、人员与部门字段、订单/审批状态字段、创建/更新审计字段。固定列名和顺序以 §2.4 的 `订单明细` 表头为准，字段值为空也必须保留列；固定表头之外的顶层原始字段保留在内部工作数据，不自动追加到交付表。

#### 2.2.2 子表字段范围

子表必须输出“固定子表头”中的全部字段：父订单关联字段、子表结构字段、价格与数量字段、产品/服务字段、版本与描述字段、购买方式/收入类型/售卖类型/服务等级/币种/单位等选项字段、客户字段、公式金额字段、`子表行ID` 和 `字段 price_sub`。固定列名和顺序以 §2.4 的 `订单子表明细` 表头为准，字段值为空也必须保留列。

除固定表头外，子表行对象中出现的每一个原始键都必须保留在内部工作数据。无法识别中文名称的键不能因为它是内部 fieldId、`*_ref_*`、公式字段或当前值为空而删除；不同父 `fieldId` 下的同名子字段必须分别按各自的子字段 ID 处理，不得混用映射。除用户明确要求原始字段外，这些内部键不追加到交付表。

不得用只覆盖固定表头的硬编码字典代替上述保留规则。整理脚本遇到未命中的父顶层键或子表行键时，禁止 `continue`、静默跳过或只在日志中记录；必须保留在内部工作数据以供核验。对外交付以固定业务表头为准，不展示原始键总数、已映射键数、追加键数或字段 ID。任何脚本若没有这条内部保留路径，不能声称“字段完整”或“验收通过”。

### 2.3 字段来源、接口与映射规则

父子表整理完成后统一读取所需辅助来源，不逐订单逐行重复查询。先按下方“字段来源与接口”执行，不能只看到空值就把空值写入 Excel。辅助列表必须完整分页并校验 `data.total` 后才能用于映射。

#### 2.3.1 订单接口和响应取值

| 目的 | Skill 入口 | 实际接口/请求 | 必须保留的响应路径 |
|---|---|---|---|
| 全局订单分页 | `crm page order <JSON>` | `POST /order/page`；请求使用标准分页 JSON，`current` 从 1 开始，`pageSize` 最大 500，筛选放 `combineSearch` | `code=100200`、`data.total`、`data.list[]`；每个 list 项的全部顶层字段、`moduleFields[]`、每个 `fieldValue[]` 行对象全部保留 |
| 客户名下订单分页 | `crm acct-sub order <客户ID> [JSON]` | `POST /account/order/page`；CLI 在请求体顶层注入 `customerId`，只返回指定客户订单 | 同上；仅在用户明确指定客户维度时使用 |
| 订单详情补查 | `crm get order <订单ID>` | `GET /order/get/{订单ID}` | `data` 中全部顶层字段和 `moduleFields[]`；仅在列表确实缺用户要求字段或需核验异常时按订单 ID 定向调用 |
| 接口差异核验 | 仅在发现两个端点返回不一致时使用 | `/order/page` 是全局订单列表；`/account/order/page` 是客户维度订单列表，不能互换 | 使用同一筛选口径分别比较 `total`、订单 ID 集合和 `moduleFields`，差异要报告；全局导出默认以 `crm page order` 的 `/order/page` 为准 |

订单分页不是只取 `name`、`number`、`customerName`。父订单 `id` 是父表订单 ID；子表行 ID 只从 `moduleFields[].fieldValue[].id` 取。`fieldValue` 中除 `id` 外的每一个键都要保留，即使键是内部 fieldId、`*_ref_*` 或 `price_sub`。

#### 2.3.2 字段获取规则

每个固定字段先从订单列表/详情原始响应取值；响应不直接提供可读名称、选项标签或价格目录投影时，再按下表指定接口获取。每一行始终按“父 fieldId → 子 fieldId”定位，禁止跨子表按中文名称取值：

#### 2.3.2.1 产品、服务与 `price_sub` 的关系

这三个值不是同一种 ID，必须分开处理：

| 值 | 实际含义 | 当前已知来源 | 能否用产品字典解析 |
|---|---|---|---|
| `*_ref_*` 产品类型值 | 产品目录中的产品实体 ID，例如 `JumpServer 企业版`、`MaxKB 专业版` | 订单子表行的产品类型引用字段；产品字典 `POST /field/source/product` | 可以，按 `productId -> name` 映射 |
| “服务”字段值 | 维保/专业服务/培训服务子表所选价格目录（服务目录）主表 ID（以订单响应中的实际值为准） | 订单行的服务字段：维保 `178368304592200000`、专业服务 `178368405249700001`、培训服务 `178368413190600000`；实时 order form 对三者均标为 `dataSourceType=PRICE` | 可以。用 `POST /field/source/price` 的 `data.list[].id -> name` 映射；也可用 `POST /field/source/ref-detail` 按 `dataSourceType=PRICE` 批量核对 |
| `price_sub` | 价格目录中的价格子行关联 ID，不是产品 ID、服务 ID，也不是订单子表行 ID | 当前订单子表行对象的 `price_sub` | 不可以。只能用于 `POST /field/source/price` 返回的价格行 `products[].price_sub`/`products[].id` 精确关联 |

对任一订单子表行，按以下顺序处理：

1. 先按当前子表父 `fieldId` 和子字段 `fieldId` 保存产品类型值、服务值、`price_sub` 原值。
2. 产品类型值查产品字典；服务值查价格数据源。服务值匹配价格目录**主表** `data.list[].id`，名称取主表 `name`，不得在 `products[]` 中查服务主表 ID。订单响应中的 `optionMap` 只能作为已返回的附带投影，不能当成完整产品/服务字典，也不能因为缺少某个 ID就改用 `keyword`、伪造 `id` 条件或逐个猜接口。
3. 非空 `price_sub` 再在同一价格目录响应的 `products[]` 中按子行 `id` 或 `price_sub` 精确匹配，并用该子行补充 SKU、描述、版本、购买方式、收入类型、服务等级、税率、单位等字段。不能把价格子行的 `product` 值改写成“服务”字段值。
4. 服务名称若订单响应已附带可读值，仍须用价格数据源按 ID核验。服务 ID直接命中唯一价格主表时填写主表 `name`；未直接命中但可唯一确认所属价格目录时，填写该价格目录名称。解析路径仅保留在内部校验记录，不写入交付文件或对用户的说明。
5. 服务 ID和 `price_sub` 都无法唯一匹配时，服务名称列留白；不得猜名称、把产品名称代替服务名称或向用户展示原始 ID、未解析标记、接口或匹配过程。

| 导出字段类别 | 订单响应中的原始位置 | 订单响应不直接提供时的接口/来源 | 取值和停止条件 |
|---|---|---|---|
| 子表名称、子表行号、子表行ID | `moduleFields[].fieldId`、数组位置、行对象 `id` | 不补查 | 父 `fieldId` 映射不到表单标签时写 `字段 <fieldId>`；行无 `id` 必须报告，不得用父订单 ID 或 `price_sub` 代替 |
| `字段 price_sub` | 当前子表行对象的 `price_sub` | 不补查；它是后续价格目录关联键 | 原样保留为字符串；为空只能留空并报告，不得改名或从行 `id` 推导 |
| 产品类型 | 子表行中对应的 `*_ref_*` 产品类型 ID；父表同名字段也先读自身值 | 优先使用订单响应同一作用域的 `optionMap.product`；缺口或需要完整字典时调用 `POST /field/source/product`，入口 `crm product`，按 `data.total` 连续分页 | `optionMap` 命中直接用名称；缺口必须用完整产品字典补查。未命中不能把 ID 当中文名交付 |
| 产品 SKU、描述、购买方式、收入类型、产品版本、服务等级、税率、单位、币种、产品 | 行内同父 fieldId 作用域的原始字段；`*_ref_*` 只作关联投影，不当最终名称 | 非空 `price_sub` 时先读 `GET /price/module/form` 的 `SUB_PRODUCT.subFields[]`，再调用 `POST /field/source/price`，按表单定义精确读取匹配价格子行 | 价格目录只补订单行自身为空且价格子行确实提供的字段；自身有值优先。不得把价格子行动态 fieldId 当成缺值跳过。无法唯一匹配、价格表单不可读或价格目录未完整时，记入内部校验记录，交付表该字段留空 |
| 子表“服务” | 维保 `178368304592200000`、专业服务 `178368405249700001`、培训服务 `178368413190600000` 下的原始 DATA_SOURCE 值（价格目录主表 ID） | `POST /field/source/price`，请求体为标准分页对象；按 `data.total` 分页读取 `data.list[]`，用 `data.list[].id -> data.list[].name` 建服务价格目录字典。对少量已知 ID可用 `POST /field/source/ref-detail`，body `{"dataSourceType":"PRICE","sourceIds":["<服务ID>"]}` | 能唯一确认时输出服务名称；无法确认时名称留白。不得在交付文件或对用户的说明中展示原始 ID、反查过程或未解析标记 |

| 最终客户 | 行内 DATA_SOURCE ID 或名称 | 优先使用订单响应同一父/子字段作用域的 `optionMap`；缺口时先读取实时 order form 确认该字段的 `dataSourceType`，再调用对应数据源的 `POST /field/source/ref-detail`（`sourceIds` 批量）或其已验证分页端点。只有确认类型为 `CUSTOMER`/`ACCOUNT` 后，才可使用相应客户接口；不得仅凭字段名直接假设 `/account/page` | 只读取实际出现的 ID并批量核验；`ref-detail` 返回空只能说明该数据源当前未返回，不得直接断言客户不存在。名称缺失时交付表留空，原始值与核验结果仅留内部记录 |

#### 2.3.3 接口调用模板

订单导出使用的辅助接口没有统一的“导出”命令，调用方按以下模板执行；禁止换成未经验证的搜索接口：

```bash
# 1) 订单父表（全局导出）：保留原筛选条件，只改 current/pageSize
cordys.sh crm page order '{"current":1,"pageSize":500,"sort":{},"combineSearch":{"searchMode":"AND","conditions":[]},"keyword":"","viewId":"ALL","filters":[]}'

# 2) 单订单详情：只有列表字段不足或需要核验时使用
cordys.sh crm get order '<订单ID>'

# 3) 产品类型字典：分页读取 data.list[].id / data.list[].name
cordys.sh crm product '{"current":1,"pageSize":200,"keyword":""}'

# 4) 服务价格目录及 price_sub：表单 dataSourceType=PRICE，分页读取价格主表和 products[] 子行
cordys.sh crm raw GET /price/module/form
cordys.sh crm raw POST /field/source/price '{"current":1,"pageSize":500,"sort":{},"combineSearch":{"searchMode":"AND","conditions":[]},"keyword":"","viewId":"ALL","filters":[]}'

# 5) 已知服务 ID 的定向核验（返回 data 数组，不是分页 data.list）
cordys.sh crm raw POST /field/source/ref-detail '{"dataSourceType":"PRICE","sourceIds":["<服务ID>"]}'

# 6) 客户字典：只传实际出现的客户 ID 对应的筛选条件；需要多页时连续读取
cordys.sh crm page account '<标准分页 JSON>'

# 7) 人员和组织字典
cordys.sh crm members '{"departmentIds":["<部门ID>"]}'
cordys.sh crm org tree

# 8) 表单和 options：先刷新快照；实时诊断才调用
cordys_ext.sh sync-if-needed
cordys.sh crm form order
```

`crm raw` 只接受一个命令行 JSON body，不支持 `@-`/`-`。`GET /price/module/form` 返回价格目录实时表单：从 `businessKey=products` 的 `SUB_PRODUCT.subFields[]` 读取价格子行字段 ID、字段名、类型和 options。`/field/source/price` 返回 `data.total + data.list[]`；每个价格主表对象至少保留 `id`、`name` 和 `products[]`。服务字段值匹配主表 `id`，`price_sub` 匹配 `products[]` 中的子行 `id`/`price_sub`。`/field/source/ref-detail` 返回 `data[]`，只能用于已知服务 ID或客户 ID的定向核验，且 `dataSourceType` 必须来自实时 form；不能用 `id` 条件或 `keyword` 替代 ID核验，也不能替代全量分页字典。

#### 2.3.4 价格目录回填的具体步骤

1. 先读取 `GET /price/module/form`。定位 `businessKey=products` 的 `SUB_PRODUCT` 字段，建立 `价格子字段 ID -> 字段名/类型/options` 映射；此映射必须来自本次实时表单，不能将订单子表 fieldId 或历史价格 fieldId 写死。
2. 收集所有子表行的非空服务 ID 和 `price_sub`，去重后一次性分页读取 `POST /field/source/price`；请求沿用 `current/pageSize/sort/combineSearch/keyword/viewId/filters` 结构，分页直到首个 `data.total`，每页保留完整价格主表及其 `products[]` 子行数组。
3. 建立 `服务ID -> 唯一价格主表` 和 `price_sub -> 唯一价格子行` 两级索引；0 条或多条匹配都视为不可唯一解析，不得任选第一条。服务 ID未命中时允许沿 `price_sub -> 子行 -> 所属主表` 反查一次。
4. 对每个订单子表行，以“子表父 fieldId + 子字段 fieldId”建立目标字段上下文；只对目标行自身为空的字段应用价格行投影。按步骤 1 的价格表单字段名映射 `产品SKU`、`描述`、`购买方式`、`收入类型`、`产品版本`、`税率`、`单位`、`服务等级`、`币种` 和 `产品` 到同名固定交付列；SELECT/RADIO 用价格表单自身 options 转标签，DATA_SOURCE 产品值用产品字典转名称。“服务”字段不因价格子行存在而自动回填。
5. 回填后再做产品字典和 option label 映射；金额、数量、折扣、公式结果、`id`、`price_sub` 不参与价格目录覆盖。对每条已唯一匹配 `price_sub` 的订单行，价格子行中非空的可回填字段必须在交付表对应列有值；否则验收失败，不能交付为完整导出。
6. 记录内部回填审计：订单 ID、订单编号、子表名称、子表行 ID、原始服务 ID、`price_sub`、服务名称解析方式、回填字段、来源价格行 ID；服务 ID和 `price_sub` 都未命中时，服务名称留白。该审计不作为交付内容，其他未回填字段也不向用户展示技术原因。

只有完成 `服务ID -> 唯一价格主表` 和 `price_sub -> 唯一价格子行` 的精确索引，并核对对应主表/子行的全部业务字段后，才能把某个服务或产品属性报告为“价格目录不存在”或“孤立未映射”。服务 ID 是价格目录主表 ID，`price_sub` 是价格目录子行关联键，二者不能混用；产品字典只解析产品实体 ID。价格目录索引未建立、匹配不唯一或回填逻辑未执行时，必须报告为“映射核验未完成”，不能报告为“验收通过”。

### 2.5 导出验收

交付前在内部核验父订单数、子表行数、页数、首个 `total`、去重数量、两表结构、父子关联、字段覆盖、产品/服务/客户映射、价格目录回填和未解析值。对用户只说明导出范围、两张表是否已生成及记录数量；不得披露反查、映射缺口、覆盖率、原始 ID、字段 ID、接口、分页或内部审计细节。用户明确要求排查数据问题时，才按其指定范围说明必要的技术信息。只检查固定列、只抽查几行、只统计行数或只验证 optionMap 都不足以通过内部验收；缺任一项都只能报告为部分结果，不能声称完成完整导出。
