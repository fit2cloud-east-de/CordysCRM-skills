# 创建订单 SOP

> 本文档是**创建订单**的唯一业务流程权威。用户说“创建/新建订单”“按合同生成订单”“拆订单”时先读本文档；查询或更新已有订单仍走 `core/query-engine.md` / `core/write-engine.md`。
>
> 通用字段结构、确认红线和失败处理继续复用 `core/write-engine.md` §0.2、§0.4、§7、§8；订单专属规则与其冲突时以本文档为准。

## 0. 当前边界

- 不按合同类型判定是否拆单；对目标合同的六类业务子表统一执行确定性分组。
- 分组键固定为：**具体产品/服务 ID + 收入类型中文标签**。同一组合的多条合同子表行合并到同一张订单，不同组合分别生成订单；每张订单只携带本组合源行。
- “产品”或“服务”取合同子表中未带 `resourceFieldId` 的具体 DATA_SOURCE ID；“其他”子表没有产品/服务选择器时，以其“产品类型”ID 作为具体产品 ID。收入类型必须先由合同 option ID 归一为中文标签再参与分组。
- 每张订单仍使用 §1.1 的既有名称模板，**订单名不追加收入类型**。
- 一次 `crm create order` 必须覆盖合同全部有效业务子表行并顺序创建全部分组。全部订单成功后才把合同“是否已拆订单”更新为“是”；不自动回写子表“关联订单编号”。
- 合同已是“是否已拆订单=是”时创建前关闭失败，防止重复订单。部分成功或状态不明时停止后续组并返回已创建订单 ID，禁止整批自动重跑。

## 1. 固定业务规则

按以下优先级组装字段：**订单名固定模板与合同继承规则 > 用户显式输入 > 本 SOP 默认值 > 表单校验**。负责人、收入类型和服务属于合同继承规则，用户不得用任意值覆盖。

### 1.1 订单名

- 不让用户自由填写订单名，也不把订单名本身列为待补充项；SOP 必须在确认前自动组装并展示完整名称。
- 每张最终订单 POST 请求体顶层 `name` **不能为空**，由 CLI 自动生成并校验，固定格式为：`<合同编码>-<产品类型中文标签>-${订单编号}`。外层自动拆单请求不手填自由格式 `name`。
- 示例：`DQ20260805X004-JumpServer 企业版-${订单编号}`。
- 第一段取本张订单 `moduleFields` 中“合同编码”字段的实际值；第二段取本张订单用于命名的产品类型**中文标签**，不得使用产品 ID。
- 第三段 `${订单编号}` 是固定字面量，必须原样交给后端；本地不得插值、替换成真实编号或删除 `$`、`{`、`}`。
- 一张订单必须先确定唯一的命名产品类型。CLI 用本组合同源行的“产品类型”ID查询当前产品目录取得中文名；缺合同编码、缺产品类型、产品 ID 无法唯一反查中文标签，或同一分组对应多个产品类型时，必须在首次 POST 前停止，不得猜测。
- 用户要求手工指定其他名称时，说明当前 SOP 只允许固定模板；不得绕过模板写入自定义名称。

### 1.2 缺省字段

| 业务字段 | `forms/order.md` 表单字段 | 缺省值 |
|----------|-------------------------|--------|
| 交付团队 | 交付团队 | 线下团队 |
| 交付形式 | 交付形式 | 远程交付 |
| 正式 License 申请状态 | 正式license申请状态 | 未申请 |
| 是否专项交付 | 是否专项交付 | 否 |

执行规则：

1. 用户明确指定该字段时保留用户值；未指定或值为空时才补缺省值。
2. 先执行 `sync-if-needed`，再从当前本地 `references/forms/order.md` / `field-schema.json` 解析字段 ID 和选项 ID；不得把中文标签直接当 `fieldValue`，也不得把本文档写死成实例 ID。
3. 字段或缺省选项无法唯一解析时立即停止，不发送 create 请求，并明确指出缺失的字段或选项。
4. `crm create order` 会为每个分组生成并校验 `name` 的合同编码前缀、产品类型中文标签和固定 `${订单编号}` 后缀，并补齐缺失的四项缺省值，作为 SOP 的最后防线；上层仍须在确认表中展示每张订单实际名称。

### 1.3 合同继承与子表必填

| 订单目标 | 合同来源 | 传值规则 |
|----------|----------|----------|
| 顶层 `owner` | 合同详情顶层 `owner` | 原样传合同负责人的 **userId**；`ownerName` 只展示，不得当值传入 |
| 顶层“收入类型” | 生成本张订单的合同子表行“收入类型” | 先把合同子字段选项 ID 解析为中文标签，再在订单顶层“收入类型”选项中按标签取目标 ID |
| 订单子表行“收入类型” | 对应合同子表行“收入类型” | 按中文标签映射到目标订单父子表下的选项 ID，不得假设合同和订单的 option ID 相同 |
| 订单子表行“服务” | 对应合同子表行“服务” | 对 `维保`、`专业服务`、`培训服务` 原样传 DATA_SOURCE 服务 ID；合同/订单子 fieldId 不同，必须按“父表标签 + 子字段标签”换成订单 fieldId |

执行规则：

1. 订单负责人必须与合同负责人一致。合同详情缺少非空 `owner` 时停止；不得省略后让后端改用当前创建人，也不得传 `ownerName`。
2. 每张订单必须确定唯一收入类型。相同具体产品/服务出现多个收入类型时按标签拆成多张订单；同一分组内所有合同源行收入类型必须一致，不得任选一个或覆盖子表。
3. 顶层收入类型和每个订单子表行收入类型必须使用同一中文标签，但分别按各自目标字段的 options 解析 ID。目标标签无法唯一解析时停止。
4. `维保`、`专业服务`、`培训服务` 子表中的“服务”按业务规则视为**必填**，即使同步表单元数据把该子字段标为非必填也不得省略。合同对应行已有服务时继承其 ID；为空时一次性列入待补充项，确认具体服务 ID 后才能创建。
5. 不得用产品类型、产品 SKU、子表名称或“销售品”代替服务；也不得把合同子 fieldId 直接写进订单子表行。
6. `crm create order` 在首次 POST 前再次要求非空 `owner`、顶层收入类型、每个有效子表行的收入类型，以及含“服务”字段子表行的服务 ID；任一缺失或顶层/子表收入类型不一致时关闭失败。

#### 1.3.1 所有子表按同步 form 完整映射

- 字段映射以 `sync-if-needed` 后的本地 `references/forms/contract.md`、`references/forms/order.md` 和 `references/field-schema.json` 为依据；截图只用于发现异常，不能作为字段清单或 fieldId 来源。
- 遍历订单 form 中的**全部** `SUB_*` 父字段。当前包括“订阅”“授权及一体机”“维保”“专业服务”“培训服务”“其他”，但实现不得只为“培训服务”写分支，也不得把六个父 fieldId 写死。
- 先按父表中文标签定位合同源子表与订单目标子表，再按子字段中文标签逐列映射。合同源行中每个有值且目标子表存在同标签字段的非 `FORMULA` 业务字段都要保留，包括产品/服务、产品类型、产品SKU、产品版本、描述、购买方式、收入类型、售卖类型、服务等级、币种、成交指导价、合同约定价、税率、单位、数量、年限、折扣、最终客户等。
- 不得把源行缩减成“公式刚好能算”的最小字段集，也不得只复制订单 form 标记为必填的字段。源合同已有的可映射业务值即使在订单 form 中选填，也必须写入订单目标行。
- `SELECT` / `RADIO` 必须执行“合同 option ID → 合同中文标签 → 订单同标签 option ID”；即使多数选项 ID 恰好相同也不能直接复制。`DATA_SOURCE` 保留实体 ID；文本、数字、日期等按订单目标类型校验后保留值。
- 合同公式结果、合同侧流程控制字段“拆分规则”、回写字段“关联订单编号”和合同子表行 `id` 不复制；订单行 `id` 由后端新生成。**`price_sub` 不是新订单行 ID，而是合同 PRICE 数据源子行的关联键，必须从精确匹配的合同源行原样保留。** 所有订单 `FORMULA` 按 §1.4 由订单公式重新计算。除这些明确排除项外，合同有值字段若在订单目标子表找不到同标签字段，必须列为映射冲突，不得静默丢弃。
- 产品/服务字段带出的 `*_ref_*` 是只读引用投影，不是普通可写列。CLI 读取合同详情，用“父表标签 + 子字段标签”取得这些值供必填校验和公式计算；公式完成后从最终 POST 行中剥离，由 Cordys 根据“产品/服务 ID + `price_sub`”重新解析。不得把投影字段显式写入后端并期待其原样保存。
- 目标 form 的必填业务字段在合同源行中没有值，或源/目标父表及子字段标签无法唯一匹配时，必须在首次 POST 前一次性列出所有缺项并停止。

### 1.4 所有子表及订单主表公式必须在首次提交前算完

订单的各个子表都是独立表单，各自公式可能引用不同原字段。CLI 先按 §1.3.1 从合同精确源行生成完整的非公式业务字段；只有 `FORMULA` 结果不复制，由 CLI 在每张订单首次且唯一一次 POST 之前统一计算。

执行规则：

1. CLI 获取当前 `/order/module/form` 后，动态遍历 payload 中所有有数据的订单子表、每一行和表单内全部 `FORMULA` 字段；不得只处理“培训服务”，不得写死六张子表的 fieldId，也不得假设各子表使用同一公式。表单新增公式时，即使本地精简 schema 尚无该公式字段，也必须计算并写入最终 body。
2. 先完成每个活动子表行的全部公式，再计算订单顶层全部公式。当前至少包括：`累计原始订单金额` = 所有订单子表行“最终成交价（含税）”之和；`有效订单金额` = `累计原始订单金额 - 调整金额`。没有数据的子表对聚合贡献 `0`，不能因为截图只展示一类子表就漏掉其他类型。
3. 合同“调整金额”是本次全部订单共享的全局金额；缺值按 `0`。CLI 先以调整金额 `0` 计算每组累计原始订单金额，再按“本组原始金额 / 全部分组原始金额”比例分摊合同调整金额。除最后一组外向 0 截断到两位小数，最后一组吸收尾差，保证各单调整金额之和与合同完全一致；非零调整但总原始金额为 `0`、存在负分组金额或精度超过两位时停止且不发送 POST。
4. 公式按当前 `formula.ir` 求值，支持子表公式引用公式、主表公式引用子表聚合或其他主表公式；调用方传入的任何旧公式值都不可信，CLI 必须覆盖重算。最终 POST body 中必须已经包含每行公式结果及主表公式的实际存储位置，不能等待创建后的编辑请求补算；带 `businessKey` 的主表公式写对应顶层字段，不重复塞进 `moduleFields`。
5. 对公式最终引用的每个原始字段逐项校验：字段必须存在且非空，值必须是可计算的有限数字；`NaN`、`Infinity`、布尔值、对象、数组和非数字文本均不允许。任何除法的实际除数不得为 0。订阅年限、维保年限、订阅/维保年限、数量、税率、折扣或调整金额等只要被当前公式引用，就属于计算必需输入。`INPUT_NUMBER.numberFormat=percent` 按 Cordys 表单语义参与运算：业务值 `6` 原样保存，但公式操作数为 `0.06`，不得要求调用方篡改成 `0.06`。
6. 公式缺定义、IR 无效、引用循环、未知函数/节点/运算符、源字段缺失、非有限数字、除 0 或结果无法按当前精度保存时，关闭失败并且不发送 POST；错误必须指出主表/子表、行号、公式和源字段，便于一次补齐。
7. 精度优先使用当前公式定义；未显式提供时按当前 CRM 行为保留两位小数并向 0 截断。示例：`6500 / 1.06` 写为 `6132.07`，对应税额写为 `367.92`。
8. 子表行 `id` 由创建成功后的系统生成，创建前不得复制合同源行 `id`；`price_sub` 必须从匹配的合同 PRICE 源行继承并随 create 提交。两者不能再作为同一类“后端生成字段”处理。
9. 当前“累计原始订单金额”的 form 字段带 `businessKey=amount`，因此计算结果写请求顶层 `amount`；“有效订单金额”没有 businessKey，继续写 `moduleFields`。实现按当前 form 的 `businessKey` 动态决定存储位置，不写死字段 ID。

## 2. 创建流程

### 步骤 1：定位唯一合同

1. 执行 `cordys_ext.sh sync-if-needed`。
2. 用户给出合同 ID 时直接 `crm get contract <ID>`；只有名称或编码时先 `crm page contract` 定位。
3. 0 条时停止；多条时展示合同名、合同编码、客户、合同类型相关字段，让用户选择；禁止猜合同 ID。
4. 读取合同详情，取得 `contractId`、`customerId`、合同编码、`owner`、`ownerName` 及全部目标合同子表完整行；不要只读取扁平化产品列表。

### 步骤 2：核对已有订单

- 已知 `customerId` 时执行 `crm acct-sub order <customerId>`，在返回记录中核对 `contractId`、订单编号、产品和金额。
- 创建前不得把含固定 `${订单编号}` 占位符的待提交 `name` 当作唯一查重条件；应以 `contractId`、客户、产品和创建时间等字段核对。
- 当前接口无法可靠按合同列出订单时，不得宣称“该合同没有订单”；在确认表中写明已完成客户维度核对及其限制。

### 步骤 3：形成订单草稿

1. 读取同步后的 `references/forms/contract.md` 与 `references/forms/order.md`，取得两侧顶层字段、全部子表、必填规则和 SELECT/RADIO 选项；不要从截图整理字段清单。
2. 遍历合同详情中全部有效业务子表行，按“父表标签 + 子字段标签”定位订单目标子表；完整保留源行上下文，不要凭相似 fieldId 或扁平化同名字段复制。合同“产品表格”是汇总表，不生成订单行。
3. 对每行提取具体产品/服务 ID、产品类型 ID 和收入类型中文标签，以 `(具体产品/服务 ID, 收入类型标签)` 分组；同组多行合并，不同组形成不同草稿。禁止让模型自行任选或合并组合。
4. 为每组用产品类型 ID 查询当前产品目录，按 §1.1 的原模板组装完整 `name`；名称不追加收入类型。随后应用四项缺省值。
5. 按 §1.3 继承合同负责人，并将本组收入类型标签分别映射到订单顶层和本组全部目标子表行。
6. 对 `维保`、`专业服务`、`培训服务` 的每个目标行继承非空服务 ID；缺服务时停止，不得提交空行。
7. 按 §1.3.1 映射本组源行全部有值的非公式业务字段，而不是只传价格、数量、收入类型和服务；不同子表的同名子字段不得混用。不要复制合同源行 `id`，但必须保留其 `price_sub`。
8. 每组先按调整金额 `0` 重算子表和主表公式，再按 §1.4 的比例规则分摊合同全局调整金额并二次重算有效订单金额。全部草稿和公式必须在首次 POST 前形成；任一组失败时本批写请求为 `0` 次。

### 步骤 4：校验并一次性补充

- 对照同步后的 contract/order form 校验 `customerId`、`contractId`、`owner`、顶层收入类型、目标子表完整行、源合同所有有值业务字段均已映射、每行收入类型、服务 ID、其他必填字段、SELECT 选项和金额；同时核对当前公式引用的价格、数量、年限、折扣、税率、调整金额等原字段均有非空且可计算的有限数字，除数不为 0。
- 一次性列出所有无法从合同、用户输入和现行规则确定的字段；不要逐字段追问。
- 不向用户追问自由格式的 `name`；但缺少组装 `name` 所需的合同编码或唯一产品类型中文标签时，必须列入待补充信息并停止提交。

### 步骤 5：展示并确认

创建前必须展示：合同、客户、预计创建订单数，以及每张订单的产品/服务、金额和全部业务字段。至少明确显示以下十二项：

| 字段 | 值 | 来源 |
|------|----|------|
| 订单名 | `<合同编码>-<产品类型中文标签>-${订单编号}` 的完整待提交值 | 固定模板 |
| 负责人 | 合同负责人姓名 + userId | 合同 `ownerName` + `owner` |
| 顶层收入类型 | 从目标合同子表行解析出的唯一中文标签 | 合同子表继承 |
| 子表收入类型 | 每行标签及订单目标选项 ID | 合同子表继承/目标字段映射 |
| 服务 | `维保`、`专业服务`、`培训服务` 每行的服务名称 + 服务 ID | 合同子表继承；必填 |
| 调整金额 | 本组按原始金额比例分摊值；最后一组吸收尾差 | 合同全局调整金额/CLI 计算 |
| 累计原始订单金额 | 全部目标子表最终成交价（含税）之和 | 主表公式预计算 |
| 有效订单金额 | 累计原始订单金额 - 调整金额 | 主表公式预计算 |
| 交付团队 | 线下团队或用户指定值 | 默认/用户 |
| 交付形式 | 远程交付或用户指定值 | 默认/用户 |
| 正式 License 申请状态 | 未申请或用户指定值 | 默认/用户 |
| 是否专项交付 | 否或用户指定值 | 默认/用户 |

用户回复“确认”或“提交”后才执行。多张订单必须先展示精确数量和逐单划分，一次确认只覆盖当前展示的草稿；字段或数量变化后重新确认。

### 步骤 6：组装并顺序提交

一次确认对应一次自动拆单请求。调用方只传唯一合同 ID，以及需要覆盖四项默认值的公共订单字段；**不要手传 `name`、`owner`、产品、收入类型、调整金额、订单子表行、公式或 `moduleFormConfigDTO`**。这些分组相关字段全部由 CLI 从合同详情生成：

```json
{
  "contractId": "<合同ID>",
  "moduleFields": [
    {"fieldId": "<交付团队字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<交付形式字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<正式license申请状态字段ID；可省略>", "fieldValue": "<用户指定选项ID>"},
    {"fieldId": "<是否专项交付字段ID；可省略>", "fieldValue": "<用户指定选项ID>"}
  ]
}
```

请求固定通过 UTF-8 stdin 提交：

```bash
printf '%s' '{"contractId":"<合同ID>","moduleFields":[]}' | cordys.sh crm create order @-
```

- CLI 在首个写请求前一次性读取订单 form、合同详情、产品目录和合同 form，生成全部分组的最终 POST body；任一字段、映射、产品名称、`price_sub`、公式或金额分摊不能完成时本批写请求为 `0` 次。
- 最终每张订单都必须含现有模板 `name`、合同 `owner/customerId/contractId`、本组唯一顶层收入类型、本组全部子表行及其 `price_sub`、分摊调整金额、全部子表与主表公式，以及当前 `moduleFormConfigDTO`。名称末尾仍是固定字面量 `-${订单编号}`，不包含收入类型。
- 多张订单按合同源行首次出现的分组顺序逐张创建，不并行提交；每张最多发送一次 POST，取得 `code=100200` 且非空 `data.id` 后才创建下一张。
- 任一订单失败或状态不明时立即停止，输出已创建订单 ID、失败分组和未执行分组，并标记 `retryAllowed:false`；不得整批自动重跑。
- 只有全部订单均成功，才读回最新合同、保全完整顶层字段和子表、附加当前合同 `moduleFormConfigDTO`，将“是否已拆订单”更新为“是”。该合同 update 最多发送一次；失败时不得重新创建订单，只能查证后单独处理合同标记。
- `splitByProductIncome:false` 只保留给旧版已物化单订单 payload 的兼容诊断；运行时 SOP 不得使用它绕过自动拆单。

### 步骤 7：核验结果

- `code:100200` 才视为成功，保存订单 ID，并用该 ID 执行一次 `crm get order <ID>`，核对负责人、顶层收入类型、目标子表全部业务字段与公式结果，以及累计原始订单金额、有效订单金额已落库；响应未返回后端替换占位符后的订单名/编号时一并核对。
- HTTP 500、超时或状态不明时，先按客户维度重新查询订单，并结合 `contractId`、创建时间、产品和金额核对；未确认未落库前禁止重试。
- 批次响应中的 `createdOrders` 是已确认成功的订单清单；无法证明成功或失败时停止后续订单创建，向用户报告已成功数量、状态不明分组和未执行数量。`retryAllowed:false` 表示禁止重新运行整个 `crm create order`；若仅合同回写失败，先查证后只处理合同字段。
- 全部创建及合同回写成功时，响应必须同时满足 `code:100200`、`writeState:complete`、`contractSplitUpdated:true`，并返回每张订单的分组键、名称、金额和 `orderId`。

## 3. 当前拆单规则摘要

| 规则项 | 当前行为 |
|--------|----------|
| 合同分类 | 不按合同类型分支；所有目标合同统一处理 |
| 分组键 | 具体产品/服务 ID + 收入类型中文标签 |
| 同组多行 | 合并到一张订单，保留全部源行 |
| 订单名称 | 继续 `<合同编码>-<产品类型中文标签>-${订单编号}`，不追加收入类型 |
| 字段继承 | 合同 owner/customerId/contractId + 本组完整非公式子表字段；保留 `price_sub` |
| 公式 | 每组独立重算全部子表公式、累计原始订单金额和有效订单金额 |
| 调整金额 | 按各组原始金额比例分摊，除末组外向 0 截断两位，末组吸收尾差 |
| 创建顺序 | 首次出现顺序串行；任一失败/不明立即停止，禁止整批重跑 |
| 合同回写 | 全部订单成功后才把“是否已拆订单”更新为“是”；不回写子表关联订单编号 |
