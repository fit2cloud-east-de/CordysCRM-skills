# 查询生成引擎

本文件是所有 CRM 列表、统计、排名和分布查询的统一编排入口。它不提供固定看板模板，也不规定用户必须查询哪些指标；它只保证自然语言、业务字段与最终请求一致。

## 1. 查询生成顺序

1. **保留用户原始语义与范围**：先判断用户指定的是本人、具体负责人、团队/部门还是公司，再判断问的是当前状态还是某段时间内发生的业务事件；不要用角色默认范围覆盖用户明确范围，也不要看到"本周复盘"就给所有指标机械追加 `WEEK`。范围判定规则以 `core/role-engine.md` §2.4 为唯一权威。
2. **确定模块与业务事件**：例如"新建商机"是商机创建，"赢单"是商机结束，"实际回款"是资金到账，"录入回款"是记录创建。池/私海术语按 `core/query-pools.md` 先锁定业务对象；跟进记录/计划列表是全局模块（见下方例外）。
3. **先刷新实例快照**：确定模块后、读取任何 forms 或视图目录前，先执行一次 `cordys_ext.sh sync-if-needed`。它以 `.last_sync` 判断 6 小时 TTL；未过期只读本地时间戳，过期才尝试刷新全部受支持模块的表单、字段 schema 与实例自定义视图。单个模块失败时保留其本地旧快照并继续其他模块；整体同步异常只告警，不阻断查询。`crm page` / `page-summary` / `search` / `view` / `follow ... page` 在联网前也会执行同一检查作为 CLI 兜底。
4. **加载模块事实**：同步尝试结束后读取 `references/forms/{module}.md`，取得真实字段名、类型、选项值、业务时间口径与该模块的官方/自定义视图目录。失败模块读取保留下来的最后有效本地快照；构造非空 `conditions` 或统计时必须使用其中的字段事实。
5. **加载条件契约**：构造条件读 `core/query-conditions.md`，按真实字段类型选择 operator/type（合法组合表在 `core/cli-reference.md`）；不得凭记忆填写。
6. **合并范围约束**：按 `core/role-engine.md` §2.4 合并权限上限与用户明确范围。需要 userId 或部门 ID 时按 `core/query-members-org.md` 取得；视图选择按 `core/query-views.md`。
7. **执行确定性校验**：CLI 会依据 `references/field-schema.json` 校验字段、type、operator、value 形状和已知枚举。CLI 对不改变语义的常见外层形状错误会先自动归一化；若退出码为 0 且响应 `code=100200`，stderr 中的"已自动归一化/无需重试"只是处理说明，直接消费响应，禁止重跑。真正失败时只按错误指出的字段、当前值形状和目标形状修改一次，不得先读脚本、发无条件探测查询或绕过校验调用裸接口；修正后仍失败才停止并报告原始错误。
8. **只依据真实响应作答**：必须读取命令 stdout 中的响应与数值；只有"运行成功"而没有响应内容，不得声称"数据齐了"或生成数字结论。
9. **保持输出边界**：直接读取 CLI 的 stdout JSON、stderr 和原始退出码。禁止在 CLI 输出后接 `| head`、`| python`、`| grep`，禁止 `2>&1`、`2>/dev/null` 或临时文件二次解析（原因见 `references/platform-notes.md` §3）。CRM 业务模块看记录或数量用 `page`，对命中范围内全部记录计算用 `page-summary`；成员、组织、跟进、日期边界使用各自专用入口。

> **跟进列表路由例外**：跟进记录、跟进计划分别读取 `references/forms/follow.md`、`follow-plan.md`，使用 `crm follow record|plan [JSON]` 请求全局 `/follow/record/page`、`/follow/plan/page`。列表命令不带父模块、不传顶层 `sourceId`；按单条线索/客户/商机缩小时，在 conditions 中分别使用 `clueId` / `customerId` / `opportunityId`。只有详情和写入继续带父 `module`。
> **成员与组织路由例外**：人名、在职名单、部门范围、层级汇总全部按 `core/query-members-org.md`，不用业务模块的 page 查人。

## 2. 存量与期间事件

- "当前、现有、进行中、阶段分布、管道"通常是**截至当前的状态**；除非用户明确限定创建期或结束期，否则不自动追加时间条件，输出时标注"截至当前"。
- "本周新增、本月赢单、今年签约、今日回款"是**期间发生的事件**；时间条件必须落在该事件对应字段，而不是统一使用 `createTime`。
- 回款记录尤其要区分：默认"本月回款/回款多少/回款排名"是资金实际发生，必须使用 `contract/payment-record.recordEndTime`；`createTime` 只回答"本月录入了哪些回款记录"，且只走 `crm page` 明细口径。CLI 会在统计请求中拒绝回款 `createTime/updateTime`。
- 同一句话可以同时包含两种口径，例如周复盘中的"本周赢单"与"当前进行中管道"；分别构造查询，不强求条件完全相同。

具体事件对应字段和状态集合只在 `references/forms/{module}.md` 维护，本文件不复制，避免形成第二套业务事实。

## 3. 硬约束与可覆盖默认

- 字段真实类型、合法操作符、枚举 value、角色权限属于硬约束，任何上下文都不能覆盖。
- forms 中的默认业务口径可被用户明确措辞细化：例如默认"回款"按实际回款时间，用户明确问"本周录入的回款记录"时才改用记录创建时间。
- 语义仍不明确且不同选择会显著改变结果时，先向用户说明歧义并询问；不要用一个貌似合理的数字掩盖歧义。
- `field-schema.json` 只负责技术契约，不决定"用户想查什么"；schema 对未知模块/字段的警告不是正确性证明，应先同步表单或核对 forms。
- `crm page` 只查询一页，默认 `pageSize` 为 `30`；纯计数传 `pageSize:1` 读取 `data.total`。`crm page-summary` 固定每页 `500` 条自动翻至 `data.total` 并在进程内流式聚合，只返回合计和有限分组摘要。完整全量倾倒和本地文件导出不是常规查询能力（唯一例外：`sop/order-operations.md`「完整订单导出」）；大量明细只能通过 `page` 按页查看或增加筛选条件。

## 4. 结果核验

- 分组/排名结果必须同时读取合计与各组 count；分组之和与合计不一致时停止下结论。
- 阶段集合必须互斥；"进行中"等排除哪些终态，以对应 forms 的业务术语为准。
- 商机"赢单/输单/成交"必须按 forms 使用 `expectedEndTime`；`actualEndTime` 只是可查询技术字段，不得因 schema 放行就把它当业务成交时间。
- 明确自然日区间必须先运行 `cordys.sh crm date-range <开始日> <结束日>`，将返回的 UTC+8 闭区间用于 `BETWEEN`；禁止用 `CST` 或宿主机默认时区手算时间戳。
- 零结果先检查字段、operator、枚举 value、时间字段和范围是否真实生效；不得随意换字段反复试到出现数据为止。
- `IN/NOT_IN` 的 `value` 即使包含多个选项，也不会改变字段类型：`stage` 的 schema 是 `SELECT`，排除成功/失败时仍写 `type:"SELECT"`。
- 输出统计结论时，至少能说明模块、范围、业务时间口径以及"截至当前"或具体期间。
