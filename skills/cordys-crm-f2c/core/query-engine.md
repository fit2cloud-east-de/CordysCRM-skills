# 查询生成引擎

本文件是所有 CRM 列表、统计、排名和分布查询的统一编排入口。它不提供固定看板模板，也不规定用户必须查询哪些指标；它只保证自然语言、业务字段与最终请求一致。

## 1. 查询生成顺序

1. **保留用户原始语义与范围**：先判断用户指定的是本人、具体负责人、团队/部门还是公司，再判断问的是当前状态还是某段时间内发生的业务事件；不要用角色默认范围覆盖用户明确范围，也不要看到“本周复盘”就给所有指标机械追加 `WEEK`。
2. **确定模块与业务事件**：例如“新建商机”是商机创建，“赢单”是商机结束，“实际回款”是资金到账，“录入回款”是记录创建。
3. **先刷新实例快照**：确定模块后、读取任何 forms 或视图目录前，先执行一次 `cordys_ext.sh sync-if-needed`。它以 `.last_sync` 判断 6 小时 TTL；未过期只读本地时间戳，过期才全量刷新八个模块的表单、字段 schema 与实例自定义视图。同步失败必须停止查询，不得继续读取旧快照。`crm page` / `page-summary` / `search` / `view` / `follow ... page` 在联网前也会执行同一检查作为 CLI 兜底。
4. **加载模块事实**：同步成功后读取 `references/forms/{module}.md`，取得真实字段名、类型、选项值、业务时间口径与该模块的官方/自定义视图目录。构造非空 `conditions` 或统计时必须使用其中的字段事实。
5. **加载操作符契约**：读取 `core/cli-reference.md`，按真实字段类型选择 operator/type；不得凭记忆填写。
6. **合并范围约束**：先遵守当前 profile 的权限上限，再使用用户明确指定的范围；只有用户未指定范围时才应用 profile 的 SELF、部门及子部门或全公司默认值。用户措辞不能越权，角色默认值也不能扩大用户明确指定的较小范围。
7. **执行确定性校验**：CLI 会依据 `references/field-schema.json` 校验字段、type、operator、value 形状和已知枚举。CLI 对不改变语义的常见外层形状错误会先自动归一化；若退出码为 0 且响应 `code=100200`，stderr 中的“已自动归一化/无需重试”只是处理说明，直接消费响应，禁止重跑。真正失败时只按错误指出的字段、当前值形状和目标形状修改一次，不得先读脚本、发无条件探测查询或绕过校验调用裸接口；修正后仍失败才停止并报告原始错误。
8. **只依据真实响应作答**：必须读取命令 stdout 中的响应与数值；只有“运行成功”而没有响应内容，不得声称“数据齐了”或生成数字结论。
9. **保持输出边界**：直接读取 CLI 的 stdout JSON、stderr 和原始退出码。禁止在 CLI 输出后接 `| head`、`| python`、`| grep`，禁止 `2>&1`、`2>/dev/null` 或临时文件二次解析；这些写法会掩盖上游失败、污染 JSON，或触发 Git Bash/Windows 路径与编码差异。查询只使用两类命令：看记录或数量用 `page`，对命中范围内全部记录计算用 `page-summary`。

### 公海 / 私海模块术语锁定（先于范围和池名匹配）

- **私海不是第三种池，也不是独立 API 模块**：`线索私海`及线索上下文中的“私海”直接锁定普通 `lead`，不得改成 `pool/lead`；`客户私海`及客户上下文中的“私海”直接锁定普通 `account`，不得改成 `pool/account`。
- 私海查询走普通模块的 `crm page lead|account` / `crm search lead|account`，不请求 `/pool/.../options`、不传 `poolId`。范围继续从用户原话确定：“我的/我名下的私海”用 `viewId:SELF`（无 SELF 时用当前 owner），“张三的私海”用 `owner=张三的 userId`，“团队/部门私海”按组织范围；只说“线索私海/客户私海”而未指定范围时使用当前角色默认值。
- 裸“私海”且同一句和当前上下文都不能判断是线索还是客户时，询问用户要查“线索私海”还是“客户私海”；不得默认到 `lead`、`account` 或任何 `pool/*` 模块。

- **先按业务对象消歧池模块**：`线索池`、`线索公海`、`线索（含公海）`、`线索(含公海)`及“线索里的公海”等明确线索上下文 = `pool/lead`；`客户公海`、`客户池` = `pool/account`。裸“公海”没有线索上下文时默认 `pool/account`；同一请求已明确在谈线索时，“公海”按 `pool/lead`。
- 锁定模块后，再请求对应的 `/pool/lead/options` 或 `/pool/account/options` 匹配池名。不同模块允许存在同名池；同名不能改变已经锁定的模块，也不能跨模块兜底。
- “东区公海”在无其他上下文时表示 `pool/account` 中名为“东区”的客户公海；“东区线索公海”或“线索里的东区公海”表示 `pool/lead`；“公海里区域是东区”才把“东区”作为记录字段条件。
- 查询某个具体池必须先从已锁定模块 options 取得 id，再执行 `crm page pool/lead|pool/account`，并把 `poolId` 作为 payload **顶层非空字符串**传入。不得放入 `combineSearch`/`conditions`，不得写成 `poolid`，不得把大整数 ID 作为 JSON 数字。CLI 在 sync 和联网前做结构预检，并在完整查询契约中再次校验。
- `crm search pool/lead|pool/account` 只用于带非空 `keyword` 的跨池搜索，不使用 `poolId`；若用户要看某个具体池或全部池记录，先取 options，再按每个 poolId 分别 page。
- 目标模块没有匹配池或返回空池时，按该模块真实结果回答；不得改查另一模块。输出 `pool/lead` 时明确写“线索池/线索公海”，输出 `pool/account` 时明确写“客户公海”，不能用裸“公海”掩盖业务对象。

### 1.1 查询范围意图（先于角色默认值）

| 用户语义 | 查询范围 |
|---|---|
| “我的 / 我负责的 / 我名下的 / 归我的”业务记录；“我有哪些 / 我有多少”线索、客户、商机等 | 在 profile 允许该模块的前提下使用模块 `viewId:SELF`；无 SELF 时用 `owner=当前用户 userId`；不加部门条件，不展开部门 |
| “我的团队 / 我的部门 / 我的下属 / 我们部门 / 团队 / 部门” | 组织范围；经理使用本部门及全部子部门，不得误判为 SELF |
| 明确指定某成员 | 在角色授权范围内使用该成员 `owner=userId` |
| 未出现本人、具体人、团队/部门或公司范围 | 应用当前角色的默认范围 |

角色定义的是权限上限和缺省范围，不是对用户原话的改写。例如经理问“我有哪些超过 7 天没跟进的线索”，两次 `latestFollowUpTime` 查询（`LT` 与 `EMPTY`）都必须使用 `viewId:"SELF"`，不能改写成 `viewId:"ALL" + departmentId`。

### 1.2 视图意图判定

- 官方视图语义（如“我的客户”“协作客户”“成交商机”）按目标模块 forms 的「官方内置视图」直接映射。
- 用户明确说“视图”“打开/切换到某视图”“按某视图统计”，或用引号引用已有名称时，按 forms 的「实例自定义视图」精确匹配；只允许唯一、已启用的命中，未命中不得猜 ID 或静默退回 `ALL`。
- **精确同名自动命中**：即使用户没说“视图”，也先去掉不改变业务含义的查询外壳（如“请/帮我/麻烦”“看下/看一下/查看/查询/查一下/列出”“给我看看”）、首尾引号、空白和句末语气词；若剩余业务文本与某个**唯一且已启用**的自定义视图名称完全一致，直接使用该 `viewId`。例如“看下销售三部本周新增线索”规范化后等于视图“销售三部本周新增线索”，必须命中该视图。
- 精确同名命中后，不得再从视图名称拆出 `departmentId`、时间等业务条件重复构造；视图内部条件由 Cordys 负责。仅叠加 profile 强制权限条件，以及用户在视图名称之外明确追加的额外筛选。
- “本月新线索”“即将到期合同”“三天未跟进客户”等普通业务短语，只有在上述规范化后**未与视图名称完全一致**时，才转换成字段条件；包含、部分重合、同义改写或模糊相似都不算精确命中。
- 多个已启用视图同名时不得猜 ID，应列出候选并让用户确认；只有禁用视图同名时不使用该视图，按普通业务条件处理并简要提示视图已禁用。
- 自定义视图可以缩小查询口径，不能扩大当前 profile 的强制范围；必要时继续叠加 SELF、owner 或部门及子部门条件。

## 2. 存量与期间事件

- “当前、现有、进行中、阶段分布、管道”通常是**截至当前的状态**；除非用户明确限定创建期或结束期，否则不自动追加时间条件，输出时标注“截至当前”。
- “本周新增、本月赢单、今年签约、今日回款”是**期间发生的事件**；时间条件必须落在该事件对应字段，而不是统一使用 `createTime`。
- 回款记录尤其要区分：默认“本月回款/回款多少/回款排名”是资金实际发生，必须使用 `contract/payment-record.recordEndTime`；`createTime` 只回答“本月录入了哪些回款记录”，且只走 `crm page` 明细口径。CLI 会在统计请求中拒绝回款 `createTime/updateTime`。
- 同一句话可以同时包含两种口径，例如周复盘中的“本周赢单”与“当前进行中管道”；分别构造查询，不强求条件完全相同。

具体事件对应字段和状态集合只在 `references/forms/{module}.md` 维护，本文件不复制，避免形成第二套业务事实。

## 3. 硬约束与可覆盖默认

- 字段真实类型、合法操作符、枚举 value、角色权限属于硬约束，任何上下文都不能覆盖。
- forms 中的默认业务口径可被用户明确措辞细化：例如默认“回款”按实际回款时间，用户明确问“本周录入的回款记录”时才改用记录创建时间。
- 语义仍不明确且不同选择会显著改变结果时，先向用户说明歧义并询问；不要用一个貌似合理的数字掩盖歧义。
- `field-schema.json` 只负责技术契约，不决定“用户想查什么”；schema 对未知模块/字段的警告不是正确性证明，应先同步表单或核对 forms。
- `crm page` 只查询一页，默认 `pageSize` 为 `30`；纯计数传 `pageSize:1` 读取 `data.total`。`crm page-summary` 固定每页 `500` 条自动翻至 `data.total` 并在进程内流式聚合，只返回合计和有限分组摘要。完整全量倾倒和运行机器本地文件导出不作为技能能力；大量明细只能通过 `page` 按页查看或增加筛选条件。

## 4. 结果核验

- 分组/排名结果必须同时读取合计与各组 count；分组之和与合计不一致时停止下结论。
- 阶段集合必须互斥；“进行中”等排除哪些终态，以对应 forms 的业务术语为准。
- 商机“赢单/输单/成交”必须按 forms 使用 `expectedEndTime`；`actualEndTime` 只是可查询技术字段，不得因 schema 放行就把它当业务成交时间。
- 明确自然日区间必须先运行 `cordys.sh crm date-range <开始日> <结束日>`，将返回的 UTC+8 闭区间用于 `BETWEEN`；禁止用 `CST` 或宿主机默认时区手算时间戳。
- 零结果先检查字段、operator、枚举 value、时间字段和范围是否真实生效；不得随意换字段反复试到出现数据为止。
- `IN/NOT_IN` 的 `value` 即使包含多个选项，也不会改变字段类型：`stage` 的 schema 是 `SELECT`，排除成功/失败时仍写 `type:"SELECT"`；只有表单字段本身为 `SELECT_MULTIPLE` 才写该类型。
- 输出统计结论时，至少能说明模块、范围、业务时间口径以及“截至当前”或具体期间。
